Furaia web dashboard development specification
Operations console  Account holder portal  Partner developer platform
Version 1.0  |  1 October 2026  |  Product and engineering specification
This document defines the complete web dashboard scope for Furaia’s internal operations team, account holders, and partner organizations. It supplies page requirements, workflows, access controls, proposed API contracts, delivery batches, and acceptance evidence so frontend and backend teams can work in parallel.
The Operations console is the main co-banking administration dashboard. Shared or joint customer accounts are not implied by that name. Joint accounts, shared pots, FX, cross-border transfers, rewards, credit, and automated advisory products require separate product specifications and are outside this dashboard release.
The specification defines required behavior. It does not certify deployed infrastructure, legal approval, security review, or live-money readiness. Existing backend capabilities described by the project checkpoints must be mapped to actual repository routes and tested before a dashboard is connected to them.

1 Scope and delivery contract
Surface | Route namespace | Primary audience
Operations | /ops | Authorized Furaia staff
Account holder | /app | Individual and business customers
Partner | /partners | Partner organization members
Public developer docs | /developers | Prospective partners and developers
Use three separately authorized application surfaces with a shared visual component library. Staff authority must never derive from a customer session or partner API key. Organization switching changes the active authorization scope and clears cached data from the prior scope. Sandbox and production are explicit environments with separate resources and credentials.
Implementation status vocabulary
Status | Meaning
Reported foundation | Project checkpoint reports the capability; route, schema, grants and tests still require repository mapping.
Required extension | A specific API, workflow or data projection must be implemented to serve this specification.
Operational verification | The code must be exercised in the target environment and evidence retained.
Outside release | An intentionally excluded product, not an unfinished page in this release.
All endpoints in this document are target contracts unless explicitly described as a reported route. HTTP route names are not proof of implementation. During the first implementation batch, create a traceability file linking each page ID to actual routes, authorization services, response schemas and automated tests. Resolve route differences through explicit mappings, not duplicate money-processing implementations.
Product defaults
Initial customer money views are KES only. Currency-aware formatting and selectors must support later registry additions without inventing multi-currency balances.
Money is processed and represented in integer minor units. The browser submits decimal-free amount_minor strings; formatting never controls accounting.
Customer account opening uses approved product and legal-entity policy. Partner access is sandbox by default and production activation requires a reviewed application.
Business account holders use organization membership and maker-checker policies for supported payment products. Business workflows are required extensions, not a claim that existing staff maker-checker automatically covers customers.
No interface can edit posted journals, manually overwrite balances, fabricate KYC approval, or treat UNKNOWN provider outcomes as failed payouts.
2 Shared experience and security
Visual system
Use restrained typography, clear table density, neutral backgrounds, strong text contrast and one Furaia accent color taken from the approved brand assets. No decorative imagery, gradient cards, glass effects, emoji navigation, animated counters or invented analytics. Use a licensed icon library with consistent stroke weight. Banking amounts use tabular numerals; IDs have copy controls and truncated display with full accessible values.
Desktop layout uses a persistent grouped sidebar, top bar with environment and scope, breadcrumbs, a page title and contextual actions. Account-holder pages collapse to a mobile navigation with Overview, Accounts, Payments, Activity and Profile. Staff and partner tables use horizontal scrolling on narrow screens with pinned identifier columns; do not compress financial columns into unreadable text.
Reusable interaction rules
Each list uses server-side filters, opaque cursor pagination, saved filter state in the URL and a stable sort. A filter change resets the cursor. Default page size 25; server maximum 100.
Each detail page displays resource status, legal entity or organization where applicable, creation/update times and the latest data timestamp. Amounts display currency explicitly.
Forms display inline field errors and an accessible summary. Required evidence uploads accept PDF, JPEG and PNG up to 10 MiB per file; the server verifies type, scans content and quarantines before review.
Every money submission has a server preview or authoritative quote, a confirmation step and a persisted client idempotency key. Double-click, browser retry and network retry reuse that key with the identical payload.
Refreshes must not replace a form the user is editing. Changed server versions require a review conflict state. Decisions and edits submit an expected_version.
Exports are asynchronous jobs, scoped to the requesting identity, with authorization checked on request and download. Show queued, running, ready, failed and expired states. Default link lifetime 15 minutes; never attach bearer credentials to URLs.
Display Africa/Nairobi by default with an explicit timezone label. Statement dates retain the provider and legal-entity calendar; API instants use UTC ISO 8601.
All content supports keyboard navigation, visible focus, accessible names, error announcements, 200 percent zoom and reduced motion. Target WCAG 2.2 AA as an acceptance requirement.
Global states
State | Required response
Loading | Skeleton of the actual layout; never show zero balance as a loading substitute.
Empty | Explain that no records exist and show the permitted next action.
No results | Keep applied filters visible and offer reset filters.
401 or session expired | Reauthenticate; preserve a non-sensitive return path and check operation status before offering a money retry.
403 | Explain permission is missing; do not expose the restricted record or offer a bypass.
Dependency unavailable | Show last successful data timestamp if available; label cached data stale and disable affected new submissions.
Money gate disabled | Keep reads, status inquiry and exact successful replays available; show whether disabled by policy or unavailable.
UNKNOWN operation | Show pending investigation, held amount and last provider evidence; never invite a second payment.
Critical reconciliation break | Staff banner identifies scope and incident reference, affected controls and permitted investigation steps.
Validation or version conflict | Retain entered values; show actionable field errors or require refreshed review before resubmission.
Authentication and session design
Use server-managed browser sessions or a backend-for-frontend with HttpOnly Secure cookies and CSRF protection. Staff federation resolves the approved staff principal and checks domain permissions on every action. Partner human login is separate from machine API credentials. Never store access tokens, API secrets or KYC evidence in localStorage, analytics events or browser error reports. Clear sensitive query caches on logout, scope switch and authorization loss.
Staff and partner sessions require MFA, with stronger step-up for credentials, approval and access changes. Proposed defaults: staff idle timeout 15 minutes and absolute duration 8 hours; customer and partner idle timeout 30 minutes and absolute duration 12 hours. Server policy is authoritative. Session expiry warnings provide a safe extension flow without granting additional permissions. Customer production authentication must replace sandbox-only credentials before public customer use.
Sensitive reveal requires scoped authorization, a reason and an audit record. Mask national IDs, contacts, addresses and beneficiary identifiers by default. Logs contain request IDs and sanitized metadata, never credentials, full identity documents or raw authorization headers. Browser code cannot decide authorization from role labels alone.
3 Roles and permission model
Role | Permitted responsibility | Restrictions
Staff Operator | Investigate scoped records and propose governed actions | Cannot approve own proposal or grant personal authority.
Staff Reviewer | Review evidence and request further information | Review permissions do not imply financial approval.
Staff Approver | Decide authorized maker-checker cases | Must be distinct from maker and excluded prior actors.
Staff Auditor | Read scoped events and approved exports | No money or policy mutations.
Staff Administrator | Manage authorized staff/access proposals | No automatic financial override or universal tenant access.
Customer Owner | Manage own identity and individual accounts | No staff or partner authority.
Business Owner | Manage business membership and authorized products | Payment approval duties depend on product policy.
Business Maker and Approver | Propose or approve scoped business payments | Distinct identities required where dual control applies.
Partner Owner | Manage organization and production-access application | Cannot self-approve production or expanded scopes.
Partner Administrator | Manage permitted apps, team and configuration | Role elevation and sensitive changes follow policy.
Partner Developer | Read docs and manage authorized sandbox integrations | Production secret access requires explicit grant.
Partner Finance | Read permitted transactions, reports and billing | No credential management by default.
Partner Viewer | Read assigned summaries | No writes or secret reveal.
Permission checks include principal, action, resource, tenant, legal entity, partner organization and environment. UI visibility follows returned capabilities; the server repeats enforcement inside the domain. Existence checks must not leak cross-tenant records. All privileged actions require reasons and evidence according to their registered case kind. Disabling or hiding a button is not authorization.

Customer capabilities: profile.manage, kyc.submit, accounts.open, balances.view, transfers.create, payouts.create, collections.create, statements.export and disputes.create. Partner capabilities: organization.manage, applications.manage, credentials.issue, credentials.rotate, credentials.revoke, webhooks.manage, logs.view, usage.view, finance.view, team.manage and production_access.submit. Map these proposed identifiers to the existing authorization registry before implementation.
4 Operations console pages
Each page inherits the shared authentication, accessibility, data freshness, error, pagination and export rules in Section 2. The contracts below are proposed targets; implementation must map them to actual services and schemas. Actions are visible only when server-provided capabilities permit them.
O01 Overview
Route: /ops. Purpose: Live operational position by legal entity and currency.
Content. Outstanding operations by state, UNKNOWN count, hold exposure, latest reconciliation run, break count, gate state, outbox lag, alert delivery state
Filters. Legal entity; date; provider; currency
Actions. Open filtered queues and incident detail; acknowledge an alert only when granted
API dependency. GET /ops/v1/overview
Acceptance. Aggregates reconcile to their source lists; freshness is visible; incompatible currencies are not summed.
O02 Customers
Route: /ops/customers. Purpose: Search and review customers within granted scopes.
Content. Customer ID, masked name/contact, tenant, state, risk tier, account count, last activity; detail includes KYC history, consents and linked records
Filters. ID; masked contact search; state; tier; tenant
Actions. Open detail, request authorized PII reveal, propose suspension or KYC review; never directly mark VERIFIED
API dependency. GET /ops/v1/customers; GET /ops/v1/customers/{id}
Acceptance. A cross-tenant search returns no restricted rows; reveals are audited; linked account access is independently authorized.
O03 Onboarding reviews
Route: /ops/onboarding. Purpose: Review submitted customer or business evidence.
Content. Application, applicant type, submitted evidence, scan status, outstanding requirements, reviewer history, policy version
Filters. State; age; assigned reviewer; applicant type
Actions. Assign review, request evidence, propose verification or rejection via registered workflow
API dependency. GET /ops/v1/onboarding; POST /ops/v1/onboarding/{id}/review-requests
Acceptance. Quarantined evidence cannot be opened; review history persists; reviewer cannot bypass final decision authority.
O04 Accounts
Route: /ops/accounts. Purpose: Inspect account lifecycle and ownership.
Content. Account ID, owner, product, currency, legal entity, state, posted/held/available balance, policy version
Filters. Owner; product; state; currency; entity
Actions. Open detail; propose suspension, closure or limit change where policy permits
API dependency. GET /ops/v1/accounts; GET /ops/v1/accounts/{id}
Acceptance. Balance labels match backend semantics; account closure with funds or active obligations is refused by server.
O05 Transactions
Route: /ops/operations. Purpose: Investigate transfer, collection and payout outcomes.
Content. Operation ID, kind, amount, fee, currency, status, business reference, provider reference, timestamps, request/correlation IDs
Filters. Kind; state; time; account; provider reference
Actions. Open timeline, related journals, holds, callbacks and evidence; authorized inquiry request
API dependency. GET /ops/v1/operations; GET /ops/v1/operations/{id}
Acceptance. UNKNOWN remains distinct from failure; provider evidence never authorizes a duplicate submission from the UI.
O06 Collections
Route: /ops/collections. Purpose: Monitor incoming collection instructions and receipts.
Content. Instruction, payer reference masked, expected/received amount, fee, receipt evidence, state and linked journal
Filters. Provider; state; date; unmatched receipt
Actions. View receipt and inbound evidence; open associated reconciliation exception
API dependency. GET /ops/v1/collections; GET /ops/v1/collections/{id}
Acceptance. Duplicate receipt shows one financial effect; unmatched receipts link to the exception workflow.
O07 Payouts
Route: /ops/payouts. Purpose: Monitor outgoing instructions and settlement.
Content. Destination masked, held amount, provider state, instruction ID, attempts, inquiry evidence and settlement due date
Filters. Provider; state; ageing; date
Actions. View instruction and inquiry timeline; open investigation; no blind resend
API dependency. GET /ops/v1/payouts; GET /ops/v1/payouts/{id}
Acceptance. Accepted timeout displays UNKNOWN and preserves hold; confirmed failure evidence is required for release.
O08 Holds
Route: /ops/holds. Purpose: Inspect reserved funds and lifecycle.
Content. Hold ID, account, operation, amount, creation/expiry times, lifecycle state, uncertainty reason, capture/release journal
Filters. State; expiry; account; operation
Actions. View evidence and lifecycle; propose any permitted exceptional action
API dependency. GET /ops/v1/holds; GET /ops/v1/holds/{id}
Acceptance. UNKNOWN-aware expiry is explained; terminal transitions cannot be forced in the browser.
O09 Ledger and journals
Route: /ops/ledger. Purpose: Read immutable accounting evidence.
Content. Journal ID, posting time, template, reference kind/ID, legal entity, currency and balanced debit/credit lines
Filters. Journal; account; reference; template; period
Actions. View linked operation/case; authorized filtered export
API dependency. GET /ops/v1/journals; GET /ops/v1/journals/{id}
Acceptance. PT-15 journals link to the maker-checker case; no edit or delete affordance exists; line totals balance.
O10 Reconciliation runs
Route: /ops/reconciliation. Purpose: Inspect ingestion and matching results.
Content. Provider, entity, currency, statement date/digest, run state, counts, equation components, alert threshold decision
Filters. Date; provider; state; entity
Actions. View observations/matches; open exceptions and amendment history; authorized ingestion request
API dependency. GET /ops/v1/reconciliation/runs; GET /ops/v1/reconciliation/runs/{id}
Acceptance. Re-ingestion identity and amended-file exceptions are visible; prior completed runs are not overwritten.
O11 Reconciliation exceptions
Route: /ops/reconciliation/exceptions. Purpose: Investigate financial breaks with evidence.
Content. Exception ID, type, expected/observed amount, difference, references, age, severity, owner and resolution case
Filters. Type; severity; state; age; assignee
Actions. Assign investigation, attach evidence, propose resolution; financial correction requires a separate adjustment case
API dependency. GET /ops/v1/reconciliation/exceptions; POST /ops/v1/cases
Acceptance. Resolution does not silently post money; approved closure records evidence and the linked journal if a separate adjustment occurred.
O12 Approvals
Route: /ops/approvals. Purpose: Decide governed privileged changes.
Content. Case kind, maker, payload digest, evidence, scope, financial impact, expiry, version, decision and execution state
Filters. Kind; state; scope; maker; execution state
Actions. Approve, reject, request evidence, cancel where permitted; execution follows registered kind
API dependency. GET /ops/v1/cases; POST /ops/v1/cases/{id}/decisions
Acceptance. Own-case approval is denied server-side; concurrent decisions have one winner; BLOCKED is shown as retryable separately from approval.
O13 Manual adjustments
Route: /ops/adjustments. Purpose: Propose approved PT-15 corrections.
Content. Approved template, permitted source/destination, currency, amount, reason code, narrative, evidence and preview lines
Filters. Template; case state; reason; entity
Actions. Preview and propose; distinct approver decides; executor posts through ledger gateway
API dependency. GET /ops/v1/adjustment-templates; POST /ops/v1/adjustments/preview; POST /ops/v1/cases
Acceptance. Cannot choose arbitrary accounts outside template policy; furaia_app execution posts balanced journal with reference to case; gate denial creates no journal.
O14 Disputes
Route: /ops/disputes. Purpose: Track customer-reported transaction problems.
Content. Dispute ID, operation, complainant, category, evidence, assignee, response due date, case history
Filters. State; category; overdue; owner
Actions. Assign, request evidence, record outcome; propose correction separately
API dependency. GET /ops/v1/disputes; POST /ops/v1/disputes/{id}/responses
Acceptance. Dispute closure does not mutate a posted journal; customer sees only customer-visible notes.
O15 Partners
Route: /ops/partners. Purpose: Review partner organizations and production access.
Content. Organization, application state, verified business evidence, requested scopes, readiness checks, active apps and environment
Filters. State; organization; requested product; review age
Actions. Request evidence, approve/reject scoped access through governance, suspend credentials under controlled policy
API dependency. GET /ops/v1/partners; GET /ops/v1/partners/{id}; POST /ops/v1/cases
Acceptance. Applicant cannot activate own production; approval is bound to environment, app and reviewed scope set.
O16 Products and limits
Route: /ops/products. Purpose: Inspect and propose versioned account policy.
Content. Product code/version, entity, eligibility, currency, fees, tier limits, effective dates, active accounts
Filters. Entity; product; effective state
Actions. View policy differences and impact; propose version change through maker-checker
API dependency. GET /ops/v1/products; GET /ops/v1/policies; POST /ops/v1/cases
Acceptance. Existing accounts retain their effective policy until a controlled migration; previewed changes show affected scope.
O17 Reports and daily close
Route: /ops/reports. Purpose: Produce scoped operational and accounting reports.
Content. Close date/state, totals per currency, unresolved breaks, outstanding holds, UNKNOWN ageing, report version and data watermark
Filters. Report type; date; entity; currency
Actions. Generate/download authorized reports; request daily-close assessment
API dependency. GET /ops/v1/reports; POST /ops/v1/exports; GET /ops/v1/daily-close
Acceptance. Close blockers are explicit; report is reproducible from its snapshot; no UI click labels an unresolved day reconciled.
O18 Audit trail
Route: /ops/audit. Purpose: Explore immutable events and integrity evidence.
Content. Timestamp, actor, action, resource, outcome, request/correlation IDs, event digest and verification result
Filters. Actor; action; resource; outcome; time
Actions. View sanitized metadata; authorized export; request integrity verification
API dependency. GET /ops/v1/audit-events; GET /ops/v1/audit-verifications
Acceptance. Integrity status distinguishes verified, failed and not checked; absence of an audit row for a rolled-back transaction is not fabricated.
O19 Staff and access
Route: /ops/staff. Purpose: Inspect staff membership and governed grants.
Content. Staff principal, active identity binding, roles, tenant/entity grants, MFA state, access expiry and history
Filters. Role; state; scope; expiry
Actions. Propose provisioning, grants, revocation; show access preview and separation duties
API dependency. GET /ops/v1/staff; GET /ops/v1/role-matrix; POST /ops/v1/cases
Acceptance. No self-elevation; disabled staff cannot reuse sessions; external SSO groups alone do not authorize money.
O20 Integrations
Route: /ops/integrations. Purpose: Inspect rail and KYC adapter readiness.
Content. Provider, capability manifest version, credential reference, certification state, callbacks health, statement lag
Filters. Provider; environment; health
Actions. View certification evidence; propose configuration or key rotation; no secret display
API dependency. GET /ops/v1/integrations; GET /ops/v1/integrations/{id}
Acceptance. Fake and certified adapters are unmistakable; secrets are represented by references only.
O21 Alerts and delivery
Route: /ops/alerts. Purpose: Investigate governance and platform alarms.
Content. Alert type, scope, threshold/window, first/last occurrence, delivery attempts, SNS message reference and recovery
Filters. State; severity; type; environment
Actions. View evidence, acknowledge if granted, open incident; delivery retry only if authorized
API dependency. GET /ops/v1/alerts; POST /ops/v1/alerts/{id}/acknowledgements
Acceptance. Delivery acceptance is not labeled email receipt; repeated alarms deduplicate and recovery history remains.
O22 Settings and governance
Route: /ops/settings. Purpose: Inspect environment and controlled runtime policy.
Content. Environment, deployed version, gate state/age, last validation, feature policy version, currency registry and notification preferences
Filters. Environment; policy kind
Actions. Edit personal notification preferences; link to controlled flag deployment and key rotation procedures
API dependency. GET /ops/v1/governance; GET /ops/v1/settings; PATCH /ops/v1/me/preferences
Acceptance. Production-impacting changes do not bypass external two-person deployment approval; stale true is never shown as permission to write.

7 End to end workflows
Customer onboarding and account opening
Registration creates an identity and a contact-verification challenge. After verified contact, the customer submits the policy-selected identity fields and scanned evidence. The server moves the application through NOT_STARTED, EVIDENCE_PENDING, PROVIDER_PENDING, REVIEW, VERIFIED, REJECTED, EXPIRED or SUSPENDED using allowed transitions. The portal shows required remediation; it does not infer approval from an uploaded document. Synthetic verification stays within sandbox.
A VERIFIED customer requests an eligible product with its terms and policy version. Account opening checks legal entity, currency, tier and account-count policy inside one transaction, creates the customer liability account and its zero projection, records consent and returns the stable account identifier. Failure rolls back the entire opening. Material KYC expiration or suspension blocks affected new commands according to policy while retaining access to records and support.
Money submission and exact replay
The portal obtains a server preview containing amount, fees, source, destination, applicable policy and expiry. Confirmation sends an immutable payload and a new Idempotency-Key. A network failure preserves the key and payload; status lookup or identical retry resolves the result. A FINAL match replays its stored response even when new writes are disabled. A changed fingerprint returns IDEMPOTENCY_CONFLICT. A denied new command consumes no key and creates no financial effect.
Payout submission returns 202 and status_url after hold, operation and outbox commit. Provider submission runs after commit. Accepted does not mean settled. UNKNOWN retains the hold and inquiry path until authoritative evidence arrives. Collection account credit occurs only through receipt processing and posting. The UI polls with bounded exponential backoff, beginning at 2 seconds and capped at 30 seconds while visible; server Retry-After takes precedence. On background tabs stop polling and resume with a status read.
Manual correction and exception resolution
An operator selects an approved adjustment template and compatible accounts, enters integer amount, reason and evidence, and reviews balanced posting preview. Proposal freezes payload and digest. A different authorized checker reviews the exact payload and decides with a mandatory reason. The executor revalidates digest, scope, account state, funds and money gate, then calls the restricted posting gateway. Journal reference_kind is maker_checker_case and reference_id is the case ID. BLOCKED gate outcomes are retryable with no journal; successful execution replay cannot post again.
A reconciliation resolution is nonmonetary unless it explicitly links a separate approved adjustment. Closing an exception records evidence and decision history. It never edits provider observations, replaces the original statement, or writes a balance. A late conflicting provider outcome reopens or creates an investigation according to the backend contract.

Partner lifecycle states are DRAFT, CONTACT_VERIFIED, SUBMITTED, REVIEW, EVIDENCE_REQUIRED, SANDBOX_ACTIVE, PRODUCTION_REVIEW, PRODUCTION_ACTIVE, REJECTED, SUSPENDED and CLOSED. Sandbox entitlement is also stored independently so KYB review does not erase test access unintentionally. Organization status, app status and credential status are separate records. Suspension disables the applicable financial delegation and credentials while preserving authorized records and support.
Credential lifecycle
Issue credentials only for an authorized application, environment and subset of granted scopes. Generate secrets server-side using cryptographic randomness and display them once after step-up. The default lifetime is 90 days unless commercial/security policy specifies less. Rotation creates a successor and a maximum 24-hour overlap recorded in policy; emergency revocation has no overlap. Revocation must be authoritative or propagated within a measured 60-second maximum; money commands must not rely on an indefinitely cached credential grant. Never recover or email an existing secret.
Partner webhooks
Events have a stable event_id, type, schema_version, occurred_at, environment, application_id and sanitized resource body. Initial event catalog: operation.accepted, operation.succeeded, operation.failed, operation.unknown, account.opened, verification.updated, production_access.updated and credential.expiring. Subscribe only to approved events and delegated resources. The provider callback authenticating inbound rail events is separate from these outbound partner webhooks.
Sign raw body plus timestamp and event ID using the approved HMAC scheme or a separately documented asymmetric scheme. For the default HMAC contract use X-Furaia-Event-Id, X-Furaia-Timestamp, X-Furaia-Key-Id and X-Furaia-Signature; canonical signed bytes are timestamp + "." + event_id + "." + raw_body. Verify constant-time signatures, reject timestamp skew beyond 5 minutes and deduplicate by event ID. Rotation publishes key ID and supports only a bounded overlap. A 2xx acknowledges delivery; retries use the same event ID and new attempt/signature timestamp.
Default retries occur after 1 minute, 5 minutes, 15 minutes, 1 hour, 4 hours and 12 hours, then dead-letter by 24 hours. Apply jitter and endpoint-specific concurrency limits. HTTP timeout is 10 seconds with 3-second connect timeout; retries cannot block money transactions. Reject SSRF targets, validate HTTPS certificates and suppress redirects to unvalidated destinations. Portal replay is rate-limited, audited and uses the same event identity.
Business customer approvals
Business payment proposals freeze account, beneficiary version, amount, fee, quote validity and policy version. Distinct business approver membership is checked at decision and execution. Staff permission grants cannot stand in for business customer consent. Funds are not guaranteed at approval: execution rechecks availability and either reserves/posts once or records an explicit rejection/block. Expired previews require a new proposal rather than changing approved amounts.

Request and response conventions
Authenticated scopes are derived from verified principals and membership. A supplied organization or account ID is a selector requiring authorization, never proof of permission.
GET lists return data and page with next_cursor, has_more and as_of. Filters are validated and cursor binds sort/scope/filter digest. Server uses stable created_at/id ordering unless another documented order is required.
Errors use error.code, error.message, error.details and request_id, mapped to the existing envelope if different. X-Request-Id appears on every response; Idempotent-Replayed is true only on stored replay.
Money and account-opening POST requests require Idempotency-Key with server-defined syntax and retention. Default target retention is at least 24 hours and longer than the provider retry horizon; existing ledger references remain unique permanently.
201 means created/completed under that endpoint contract; 202 means accepted for asynchronous work with status_url; 409 means conflict or changed idempotency payload; 422 means invalid business request; 429 means enforced throttling; 503 means gate/dependency unavailable.
PATCH and case decisions submit expected_version. A conflicting version returns 409 VERSION_CONFLICT; the client reloads and asks the user to review changed data.
Reject unknown money-command fields and bound request bodies. Quotas return RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset; 429 includes Retry-After. Headers derive from real enforcement when that subsystem lands.
OpenAPI defines security, required scopes, all request/response schemas, enum values, examples, errors, pagination, amount encoding and idempotency. Generate client types and contract fixtures from it; preserve backward-compatible additions under /v1.

Performance and data quality acceptance
Proposed staging test targets: authenticated shell usable within 2 seconds on a representative 4G connection; p95 read API responses below 500 ms excluding separately measured external dependencies; asynchronous submit acknowledgement below 1 second excluding deliberate upstream calls, which must not occur inside money transactions. Exercise 100 concurrent users per surface as an initial load profile, then revise from actual forecast. Dashboards must not issue a per-row API call for each table entry. Use aggregate/detail projections and capped polling. Large reports run asynchronously. Operator procedures
Balance drift: open scoped accounts and journals, compare authoritative projections, capture incident evidence and follow the controlled money-write pause procedure. Do not change balances directly. Provider UNKNOWN: inspect held funds and inquiry/statement evidence; do not resubmit a new payout. Reconciliation break: assign investigation, retain source digest and proposal evidence, resolve nonmonetary classification or create a separately approved adjustment. Webhook compromise: revoke/rotate the affected secret, pause scoped delivery if needed, preserve attempt evidence and notify affected partners through the incident procedure.
Access incident: revoke the identity/session/key and review recent scoped actions. Governance outage: inspect validation age, refresher lease and Redis state, distinguish MONEY_WRITES_DISABLED from MONEY_WRITES_GATE_UNAVAILABLE, restore dependencies and verify a fresh authoritative snapshot before new commands resume. Partner suspension: disable the reviewed scope without deleting transaction history; communicate status and preserve support access under policy.
Definition of complete
A dashboard batch is code complete when its full page workflows, actual contracts, domain authorization, tests and documentation pass. It is integrated when those tests run against the actual services rather than mocks. It is operationally complete when deployed identity, provider, governance, notification and recovery exercises meet acceptance. The three-dashboard release is complete when all in-scope page IDs and workflow scenarios have evidence, required extensions are implemented, and production activation has been approved for the services offered.
